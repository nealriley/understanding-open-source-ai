Chapter 0 · Primer

How Language Models Work

A model release is easier to understand when you can follow what changes during training and what stays fixed when someone uses it. The useful starting point is a pipeline, not a leaderboard.

Prerequisite check. No earlier chapter is required. In your own words, distinguish learning a recipe from following it. Keep that distinction, but remember a model learns numerical patterns rather than a human-readable recipe.

By the end

  • Annotate a pipeline with data, learned parameters, post-training and inference.
  • Distinguish a training objective from a deployment feature.
  • Identify which release artefacts support running, adapting or investigating a model.

Real-world cases reviewed 16 September 2026. Publication dates identify historical evidence, not current rankings or rules. Practice cases are fictional.

A model is an artefact inside a system

Imagine a fictional library assistant, Alder. The application receives a question, retrieves a passage from a manual, sends both to a language model and displays a response. The model is one component: retrieval chooses material, the application decides permissions, and the interface decides what readers see. If a response improves after replacing the search index, that is not evidence that the model learned new weights.

Text is represented as tokens: units selected by a tokenizer. Training adjusts numerical parameters so the model performs better under an objective. In an autoregressive language model, generation repeatedly predicts a next token from the available context. A convincing continuation is not a guarantee that a statement is true. A system may add tools, retrieval, verification and human review around that loop.

Vaswani and colleagues’ 2017 paper introduced the transformer as an attention-based architecture. Attention combines information across representations. The historical contribution does not imply that every subsequent language model has the same architecture, context handling or computational cost.

Training has stages, not a compulsory recipe

Pretraining develops a base checkpoint from broad data. Post-training adapts a checkpoint through additional training. Supervised fine-tuning uses examples of desired responses; preference methods use judgements about alternatives; reinforcement learning adjusts behaviour using rewards. RL can be part of post-training. It is not a third stage that every model must complete after post-training.

A concrete historical example is Ouyang and colleagues’ InstructGPT study (2022): demonstration data supported supervised fine-tuning, followed by rankings and reinforcement learning from human feedback. Rafailov and colleagues’ DPO paper describes a different preference-optimisation route that avoids the conventional separate reward-model/RL pipeline. These are examples of methods, not a universal production recipe.

A reward might come from people, a learned evaluator or an automatic checker. Each answers a narrower question than “is this model good?” Passing an answer checker does not establish truthfulness across domains, and satisfying a preference judge does not establish factual correctness. When reading a release report, ask what was optimised and what was evaluated separately.

Using a checkpoint is a different operation

In ordinary inference, the weights stay fixed while the input context and generated tokens change. Giving Alder a corrected passage can change its next answer without retraining. Saving that passage in a retrieval system changes what the application can supply later; updating model weights requires a training process. A product may combine all these operations, so describe the component that changed.

The bill depends on more than model size. Context length, output length, batch size, hardware, numerical precision, memory traffic and utilisation affect serving. A hosted price also reflects a supplier’s commercial choices. A small price quotation cannot establish the full cost of owning and operating an alternative. Include deployment engineering, monitoring, human review and idle capacity.

Optional depth: why parameter counts are an incomplete cost model

A mixture-of-experts model routes tokens through selected components. Active parameters help describe work per token, while total weights still matter for storage and memory. Full pairwise attention compares many token pairs; saying that its interaction count grows quadratically does not specify an entire implementation’s latency or memory use. Caching and alternative attention arrangements change practical behaviour.

Hoffmann and colleagues (2022) studied how to allocate a training compute budget between model size and data. The lesson is to state the budget and assumptions. Their empirical relationship is not a calendar predicting when a later open release will match a proprietary product.

More computation can enter at several points

A system can generate intermediate reasoning, try several answers or call tools. These use computation during deployment. They do not by themselves show which training method produced the model. Generated reasoning can contain errors, and a successful tool call may depend on a carefully engineered environment. Evaluate the whole workflow you intend to deploy.

Training data can itself be generated

A teacher model can provide examples or feedback to train a student. This is a family of distillation methods. Synthetic data can also supply tasks, preferences or filtered material. Identify the information flow rather than assuming that any generated data has the same purpose. Chapter 7 examines what a controlled experiment would need to show about its benefit.

What would you need from a release?

To run a model, look for compatible weights, tokenizer, configuration and inference software. To adapt it, inspect training tools, data permissions and hardware requirements. To investigate its development, look for data documentation, training code, evaluation details and intermediate checkpoints. These are separate requirements: a runnable download is not a complete research record.

For Alder, place the tokenizer before model input, the base weights after pretraining, adapted weights after post-training, and retrieved passages alongside each inference request. Then place the licence around the actual artefacts it covers. The same release can be useful for deployment while leaving important research questions unanswered.

Put the argument to work

Draw or write Alder’s pipeline: broad data → pretraining → base checkpoint → optional adaptation → released checkpoint → inference with a retrieved manual → response. Mark which steps change weights. Add a tokenizer, an evaluation step, and two artefacts needed by a researcher that an end user might never download.

Compare your reasoning with the feedback

Pretraining and adaptation change weights; ordinary inference and retrieval do not. The tokenizer maps text to model inputs. Evaluation measures behaviour rather than necessarily updating weights. Training-data documentation and intermediate checkpoints help investigate development. If you put RL after every post-training stage, revise it to a possible method within adaptation. If your diagram labels the entire assistant “the model,” separate retrieval and permissions.
