What 'Open' Means

A team says its model is “open.” Can you run it yourself, change it, share it, or investigate how it was trained? Those are different questions. This chapter teaches you to turn the label into a checkable description of a particular release.

What you will be able to do

  • Describe a release's access method, available artefacts, and permissions separately.
  • Explain why downloadable weights alone do not establish compliance with the Open Source AI Definition.
  • Write a qualified release assessment that identifies missing evidence and a next check.

Before you start: you should be able to distinguish weights, training data, and inference code. If these are unfamiliar, revisit Chapter 0: what is in a release. Allow about 20 minutes to read, plus 10–15 minutes for the activities; these are estimates.

1. Start with access

Irene Solaiman's 2023 release framework describes six access levels, from a system kept inside a lab to a fully open release. It helps us ask who can interact with a system and how much control the provider retains. The levels describe release arrangements, not a ranking of model quality or a licence certification.

A release can offer both an API and downloadable weights. Record both. If a download only works under additional hardware or access restrictions, describe those restrictions rather than forcing the release into one box.

2. Inspect the artefacts and define your terms

Open weights: a distribution description

In this book, open weights means that trained parameters are available to download. Check separately whether the release includes what is needed to run them, what its terms permit, and what hardware is required. A weights file alone does not disclose the training process.

Open Source AI: a specified definition

The OSI Open Source AI Definition 1.0 combines freedoms to use, study, modify, and share with access to the preferred form for modification. For machine-learning systems, it specifies data information, code, and parameters, with requirements on their terms. A permissive licence on one file does not establish that the complete release meets the definition.

The data requirement is more precise than “publish every raw training file.” OSI's FAQ on data distinguishes shareable, public, obtainable, and unshareable data. It also explains that the definition does not mandate full reproducibility. Check the actual disclosures against the definition; neither a missing raw dataset nor a marketing label is a sufficient assessment.

Research transparency: ask what can be studied

The OLMo paper describes releasing training data and training and evaluation code alongside weights. Pythia provides checkpoints across training and tools to reconstruct the training data order. These artefacts support investigations that final weights alone cannot support. They do not remove the need for computing resources or a reproducible environment.

Fully open is used here as shorthand for a broadly documented research release. Always list the actual artefacts. It is not a separate certification, and material transparency and permission to reuse remain separate questions.

3. Read the permissions for the exact release

Use the licence attached to the specific version and component. A repository's code licence need not govern its weights or datasets. Read incorporated policies and additional conditions, too.

These are reading prompts, not complete summaries of the agreements. “Free to download,” “commercial use permitted,” and “meets a named open-source definition” are different claims.

4. Worked example: assess a release

Invented teaching case: Cedar-7B offers downloadable weights, inference code, and a model card. The weights and inference code each carry MIT terms. Its card lists evaluation results, but no training code or data information is provided.

  1. Access: the weights are downloadable. Cedar also needs a compatible runtime and sufficient hardware to run locally.
  2. Artefacts: weights, inference code, and a card are present. Training code and data information are explicitly absent.
  3. Permissions: the case specifies MIT for two components. That tells us nothing about permission to reuse an undisclosed dataset.
  4. Conclusion: describe Cedar as an open-weights release. The missing components mean this described release does not meet the OSI definition. We cannot reconstruct its training process from the supplied package.
  5. Next check: ask whether a separate training repository and data disclosure exist; if found, reassess the complete release.

Notice the distinction between known absent and not yet inspected. In a real review, write “not located in the material inspected” when that is all your evidence supports.

5. Translate competing claims into questions

A developer may mean local deployment; a researcher may mean access to training artefacts; a policy writer may mean freedoms under a particular definition. Before arguing about the label, ask what each person wants to do and what evidence would support that use.

A useful habitReplace “Is it open?” with “What can this reader access, do, and verify with this exact release?” Openness alone does not establish safety, quality, suitability, or operating cost.

6. Your turn: a release assessment

Invented teaching case: Rowan's announcement says “fully open.” You can download weights and inspect its training code. The README links to a data document that you have not opened. Its licence permits research but prohibits commercial use. An API is also available.

Write four sentences: describe access; assess the stated permission; identify what is still unknown; and name the next document or artefact you would inspect. Explain whether the phrase “fully open” settles anything.

Compare your reasoning with the feedback

Rowan offers both downloadable and API access. Its stated commercial-use prohibition conflicts with the any-purpose freedom in the OSI definition. The data document's contents remain unknown: an unread link is not evidence of either completeness or absence. Inspect that document and the exact licence, then list the available research artefacts. The announcement does not replace those checks.

Self-check: did you keep access, permissions, and evidence separate; identify an unknown without guessing; and propose a specific next check? Correct any sentence that confuses those dimensions.

7. Carry forward a precise description

  • API or hosted access: describe the interface and provider control.
  • Open weights: record downloadability, component terms, and practical dependencies.
  • Open Source AI: name the definition and version, and document your assessment.
  • Research transparency: list data disclosures, code, checkpoints, and reproducibility limits.

Before Chapter 2, explain from memory why a weights download is insufficient to answer a researcher's question about training. Then check your explanation here. Later, use the same release assessment in the book's decision memo.
